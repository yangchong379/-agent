# 求职面试 Agent：原理、运行与简历表达

## 1. 一句话项目定义

这是一个面向企业招聘与个人求职辅导的混合式、有状态 AI Agent：它能基于简历、JD 和企业知识生成 2～6 轮自适应面试，逐轮评分并输出可审核报告；同时用本地意图路由、可解释岗位匹配、上下文压缩和长期记忆召回支持持续求职对话，千问只承担语义生成。

## 2. 可落地的完整链路

```text
简历授权录入 ── PII 脱敏 ── 结构化画像
                                 │
JD 录入 ── 来源标记 ─────────────┤
                                 ▼
                    岗位匹配分析 + 本地 RAG
                                 │
                                 ▼
                    2～6 轮自适应面试
                     │ 每轮：问题→回答→五维评分
                     │ 下一题读取之前的问答与评估
                     ▼
                    汇总报告 → 人工审核 → 审计日志

求职教练消息
   │
   ├─ 本地意图路由 + 岗位匹配分/命中词
   ├─ 最近 12 条消息（短期上下文）
   ├─ 滚动摘要（压缩的中期上下文）
   ├─ 简历画像 + 目标 JD（业务上下文）
   └─ 相关长期记忆（跨会话上下文）
          ↓
     结构化模型输出：回答 + 待保存记忆候选
          ↓
     安全过滤、去重、持久化；用户可查看/修改/删除
```

网页支持直接粘贴或上传 PDF/TXT/Markdown 简历。服务提取文本后先做基础 PII 脱敏和结构化，再保存画像；新对话第一次发消息时会自动关联最近一份简历，减少重复输入。

## 3. 核心原理

### 3.1 为什么采用“有界工作流”

招聘是高风险业务。系统没有让模型自由循环或直接决定录用，而是把流程固定为：解析、匹配、检索、提问、评分、追问、报告、人工审核。LangGraph 负责准备阶段的显式状态流转，HTTP 请求与数据库负责跨时间的面试状态。

这样做的好处：流程可预测、可恢复、可测试；模型失败不会破坏权限和状态机；任何副作用都能审计。

### 3.2 为什么使用结构化输出

模型输出先进入 Pydantic Schema。字段长度、枚举和分数范围都会被验证。模型给出的总分不会被直接相信，服务端按五个维度重新求和；多轮最终分也由确定性函数计算。

原则是：模型负责语义，程序负责规则。

### 3.3 上下文管理如何工作

不能把全部历史无限塞入模型，否则成本、延迟和上下文污染都会持续增加。本项目把上下文分成四层：

1. 最近消息：保留最近 12 条，维持当前话题的细节；
2. 滚动摘要：历史超过阈值后，将较早消息压缩为目标、事实、行动项和未解决问题；
3. 业务资料：按会话绑定简历画像和目标岗位；
4. 长期记忆：从当前问题召回相关、经过用户许可保存的持久信息。

最终提示词只装配“本轮真正需要”的上下文，而不是把数据库全部内容发送给模型。

### 3.4 记忆管理如何工作

记忆管线分为 Write、Retrieve、Inject、Manage 四步：

- Write：模型只返回 `goal / preference / experience / constraint` 四类候选；服务端再做脱敏、敏感类别过滤、长度限制和指纹去重；
- Retrieve：对当前问题和记忆做中英文关键词匹配，优先召回相关目标与约束；后续可替换为向量检索；
- Inject：只把 Top-K 相关记忆注入本轮，而不是注入全部记忆；
- Manage：提供列表、手动创建、修改、停用和物理删除接口，网页支持逐条删除。

记忆以 `tenant_id + owner_id` 双层隔离。`X-User-ID` 在演示环境默认为 `workspace-user`，生产环境应由 OIDC/SSO 的不可伪造用户身份注入。

### 3.5 RAG 与面试证据

系统先从 `knowledge/` 中检索与岗位重点相关的片段，再把带 `evidence_id` 的证据传给出题模块。RAG 用来提供内部标准和参考边界，不代表事实自动正确。输出仍需限制引用范围、做离线召回评测并由人工审核。

### 3.6 多轮面试如何自适应

每轮回答都会经过相关性、正确性、深度、工程性、表达五个维度评分。下一轮问题读取此前问答和评分，针对证据缺口追问。轮数由创建面试时的 `max_turns` 控制，范围 2～6；最后把首轮与后续轮次的平均表现确定性聚合，再生成报告。

### 3.7 安全与可靠性

- API Key + Tenant ID + User ID 隔离；
- 简历、JD 和回答进入模型前进行 PII 脱敏；
- 标记提示注入特征，并在系统提示词中把外部文本声明为不可信数据；
- 面试创建支持幂等键，避免网络重试重复创建；
- 回答提交时锁定面试记录，并用状态机拒绝重复或越序回答；
- 重要动作写入审计日志；
- AI 只给决策辅助，报告必须经过人工审核。

### 3.8 为什么不是“所有事情都交给大模型”

系统先用确定性代码识别岗位推荐、简历优化、面试准备、差距分析和行动计划等意图，再用简历技能与岗位文本计算可复现的匹配分和命中关键词。模型拿到的是已筛选的事实和工具结果，只负责解释、组织和生成建议，不能修改程序计算的分数。

真实模型通过统一适配器连接 DashScope/OpenAI；调用超时、网络异常或输出校验失败时，会自动降级到本地 Mock。这样即使外部模型暂时不可用，简历管理、岗位匹配、历史记录和页面仍可工作，不再直接返回 500。

## 4. 主要接口

| 能力 | 接口 |
|---|---|
| 简历与岗位 | `POST /resumes`、`POST /jobs` |
| 自适应面试 | `POST /interviews`、`POST /interviews/{id}/answers` |
| 报告审核 | `POST /interviews/{id}/review` |
| 求职对话 | `POST /conversations`、`POST /conversations/{id}/messages` |
| 历史上下文 | `GET /conversations/{id}` |
| 记忆管理 | `GET/POST /memories`、`PATCH/DELETE /memories/{id}` |
| 网页工作台 | `/ui/dashboard`、`/ui/coach` |

所有业务 API 都需要 `X-API-Key`、`X-Tenant-ID`；个人对话建议再传 `X-User-ID`。

## 8. 常见追问与回答要点

### 为什么不用纯聊天历史？

全量历史会造成 Token 线性增长、延迟增加、旧信息干扰和隐私暴露。分层上下文保留当前细节，用摘要保存长期主线，用检索只取相关记忆。

### 记忆和 RAG 有什么区别？

RAG 检索的是组织知识，例如面试标准；记忆保存的是某个用户明确表达的稳定背景。两者来源、权限、生命周期和删除要求不同，不能混在一个无权限边界的向量库里。

### 如何防止错误记忆？

只接受四类明确事实，不保存模型推断和敏感属性；落库前做过滤与去重；提供查看、修改、停用和删除能力。更高要求下应增加“保存前用户确认”和记忆过期时间。

### 为什么报告还要人工审核？

招聘属于高影响决策，模型评分可能有偏差。系统只提供证据和辅助建议，最终结论由授权人员作出，并保留审计记录和申诉路径。

### 下一步怎么扩展？

接入 OIDC/SSO 和 RBAC；用 pgvector/OpenSearch 替换本地检索；为长任务增加队列、超时和死信；增加模型、提示词和知识库版本；建立黄金数据集，持续评测检索召回、评分一致性、幻觉率、延迟与成本。

## 9. 当前边界

这是可运行的工程基线，不等于未经改造即可处理真实招聘数据的最终生产系统。真实上线仍需要法律与公平性评审、SSO/RBAC、密钥托管、TLS、监控告警、备份恢复、数据保留与删除 SLA，以及真实业务黄金样本评测。
